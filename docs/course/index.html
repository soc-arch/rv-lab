RV Lab practical exercises

Write a C application, prove its results on Spike and RTL, and explain its cost using actual CPU observations. These eight units can be used as weekly exercises or completed at your own pace. Each unit ends with a small record of what you observed; those records become your final experiment report.

Start with Lab 01: Setup and baseline. No CPU RTL edits are needed for this course. The lab now uses the HY-RV P1.F0.BP0.LS0.X1 core (ant_j0): frontend preparation overlaps one backend execution IR, with a depth-zero link and a static branch predictor. The application/runtime and same-ELF comparison remain the same. Read the current CPU overview.

Before you start

See the expected results and real screenshots for all eight labs for a reference before running each exercise. Run the programs yourself and record your own measurements; cycle totals belong to the core, preset, memory adapter, and tools recorded with that run. Historical teaching-core measurements are labeled.

You should be comfortable with C functions, arrays, loops, a terminal, and binary or hexadecimal numbers. The lab supplies startup code, a linker script, a small output library, and program completion. You write main() and helper functions. The machine is a freestanding RV32IM system with 1 MiB SRAM, not a Linux program.

Choose a machine and tools using the setup guide. On a laboratory server, staff provide the tool environment; a local Linux setup uses the same open-source tools. Lab 01 checks them. You do not need an FPGA or physical camera. A modern browser opens the generated result pages and cycle viewer.

Commands assume that you cloned this repository into ~/rv-lab. If you chose another directory, use that path instead. Keep your own source in student/ and generated results in build/course/. Each lesson begins with the same output selection so opening a new terminal does not silently switch experiments.

The public HTML course website provides these instructions. To run an experiment, use your Linux terminal, then open its generated results using the local server in Lab 01. Results are not generated by clicking a lesson in the public website.

Each lesson has a goal, numbered procedure, expected observations, and a checkpoint. Treat the checkpoint as a stop sign: resolve a failed correctness check before comparing performance. An expected-failure exercise explicitly tells you when failure is the intended observation.

Keep one experiment notebook

Use a text file, spreadsheet, or your course submission system. For every experiment, record the command, source version, optimization option, selected core, memory profile, result status, and output directory. For performance work, also record the ROI boundaries, cycles, retired instructions, CPI, and any assumed clock frequency. Keep generated build.json, result.json, and performance.json alongside the source. Record detailed trace limits separately from full-run measurements.

Do not copy an example's cycle totals as your own. The tools and selected CPU determine the numbers you actually measure. A successful run on Spike alone does not establish correctness on RTL; use the same-ELF comparison.

Looking something up

  • Quick application workflow: runtime API and command reference.

  • Performance contract: measurement boundaries, CSR details, CPI, and limitations.

  • Cycle viewer guide: signal meanings and all controls.

  • Custom application registration: names, refresh, and validation rules.

  • Reproducibility guide: validation receipts and release checks.

  • Published validation record: the checked teaching baseline and scope of its results.

  • Core replacement guide: staff integration boundary for a later CPU.

The course progression is inspired by the separate setup, exercise schedule, and hands-on pages in ETH Zurich's VLSI exercises. The commands, examples, and checkpoints here are written for HY-RV.
