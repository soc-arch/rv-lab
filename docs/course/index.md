# RV Lab practical exercises

Write a C application, prove its results on Spike and RTL, and explain its cost
using actual CPU observations. These eight units can be used as weekly exercises
or completed at your own pace. Each unit ends with a small record of what you
observed; those records become your final experiment report.

Start with [Lab 01: Setup and baseline](01-setup.md). No CPU RTL edits are needed
for this course. The lab now uses the HY-RV **P1.F0.BP0.LS0.X1** core (`ant_j0`):
frontend preparation overlaps one backend execution IR, with a depth-zero link
and a static branch predictor. The application/runtime and same-ELF comparison
remain the same. [Read the current CPU overview](../core-overview.md).

## Before you start

See the [expected results and real screenshots for all eight labs](../expected-results.md)
for a reference before running each exercise. Run the programs yourself and
record your own measurements; cycle totals belong to the core, preset, memory adapter,
and tools recorded with that run. Historical teaching-core measurements are labeled.

You should be comfortable with C functions, arrays, loops, a terminal, and binary
or hexadecimal numbers. The lab supplies startup code, a linker script, a small
output library, and program completion. You write `main()` and helper functions.
The machine is a freestanding RV32IM system with 1 MiB SRAM, not a Linux program.

Choose a machine and tools using the [setup guide](../setup.md).
On a laboratory server, staff provide the tool environment; a local Linux setup
uses the same open-source tools. Lab 01 checks them. You do not need an FPGA or
physical camera. A modern browser opens the generated result pages and cycle viewer.

Commands assume that you cloned this repository into `~/rv-lab`. If you chose
another directory, use that path instead. Keep your own source in `student/` and
generated results in `build/course/`. Each lesson begins with the same output
selection so opening a new terminal does not silently switch experiments.

The public HTML course website provides these instructions. To run an experiment,
use your Linux terminal, then open its generated results using the local server
in Lab 01. Results are not generated by clicking a lesson in the public website.

## Exercise sequence

| Unit | Question you will answer | Main tools | Record to keep |
|---|---|---|---|
| [01 — Setup and baseline](01-setup.md) | Can this machine reproduce the reference run? | Tool doctor, compare, smoke | Tool versions and passing baseline |
| [02 — Your first main](02-first-main.md) | Does my application calculate the right answer? | C runtime, Spike, RTL, output page | Source, checks, console output |
| [03 — Find a wrong result](03-debugging.md) | Can I distinguish a bad expectation from a bad computation? | Known-answer checks, result report | One failure and its correction |
| [04 — Register and inspect](04-cycle-viewer.md) | What does the CPU do for each instruction? | Registration script, cycle viewer | Annotated load, branch, and retirement observations |
| [05 — Measure an improvement](05-performance.md) | Did fewer cycles produce the same useful work? | ROI, CSR counters, instruction log | O0/O2 comparison and explanation |
| [06 — Change memory timing](06-memory.md) | Why can the same program take more cycles? | Memory profiles, bus timeline | Fast/latency/stall comparison |
| [07 — Process an image](07-images.md) | Can I connect visible output with a measured kernel? | Camera report, pixel reference, focused trace | Output pixels and cycles per pixel |
| [08 — Reproducible project](08-project.md) | Could another person reproduce my claim? | Separate builds, manifests, export | A small complete experiment package |

Each lesson has a goal, numbered procedure, expected observations, and a
checkpoint. Treat the checkpoint as a stop sign: resolve a failed correctness
check before comparing performance. An expected-failure exercise explicitly tells
you when failure is the intended observation.

## Keep one experiment notebook

Use a text file, spreadsheet, or your course submission system. For every
experiment, record the command, source version, optimization option, selected
core, memory profile, result status, and output directory. For performance work,
also record the ROI boundaries, cycles, retired instructions, CPI, and any assumed
clock frequency. Keep generated `build.json`, `result.json`, and
`performance.json` alongside the source. Record detailed trace limits separately
from full-run measurements.

Do not copy an example's cycle totals as your own. The tools and selected CPU
determine the numbers you actually measure. A successful run on Spike alone does
not establish correctness on RTL; use the same-ELF comparison.
